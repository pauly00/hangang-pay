# 한강페이 프로젝트 이해 가이드

## 0장. 이 문서의 목적

이 문서는 한강페이 프로젝트를 단순히 요약하는 문서가 아니라, 프로젝트를 처음 보는 사람이 실제 코드를 읽고 설명할 수 있도록 돕는 학습서다.

이 문서를 읽으면 다음을 목표로 한다.

1. 프로젝트 전체 구조를 이해한다.
2. 기능별 요청 흐름을 Controller, Service, Repository, 외부 API 순서로 따라갈 수 있다.
3. Spring Boot, Java, JPA, Redis, RabbitMQ, Outbox, Web3j가 왜 사용됐는지 설명할 수 있다.
4. 결제 시스템에서 멱등성, 동시성, 상태 머신, 복구 로직이 왜 중요한지 이해한다.
5. 면접에서 기술 질문을 받았을 때 프로젝트 사례로 답변할 수 있다.
6. 자소서와 포트폴리오에 어떤 경험으로 녹일 수 있는지 정리한다.

# 1장. 프로젝트 전체 구조

## 1.1 한 줄 요약

한강페이는 사용자가 지역화폐를 충전하고, QR로 결제하며, 가맹점이 정산/환전할 수 있는 CBDC/지역화폐 결제 플랫폼이다.

## 1.2 전체 요청 흐름

```text
사용자 또는 가맹점
 ↓
React FE
 ↓
Spring Boot BE
 ↓
Spring Boot Bank
 ↓
RabbitMQ
 ↓
Blockchain(Besu + Solidity Contract)
```

각 계층의 역할은 다음과 같다.

| 계층 | 역할 |
| --- | --- |
| React FE | 사용자가 보는 화면, QR 스캔, 결제/충전/환전 UI |
| Spring Boot BE | 인증, 세션, 사용자/가맹점 도메인, 결제 상태 관리 |
| Spring Boot Bank | 실제 계좌/지갑 원장, 블록체인 제출, 은행/BaaS 역할 |
| RabbitMQ | 블록체인 요청을 비동기로 전달 |
| Blockchain | 토큰 이동, 중복 거래 방지, 거래 불변성 확보 |

## 1.3 왜 서버를 BE와 Bank로 나눴는가

서버를 하나로 만들 수도 있다. 하지만 이 프로젝트는 플랫폼 서버와 은행/BaaS 서버의 책임을 분리했다.

BE는 사용자 경험과 서비스 정책을 담당한다.

1. 로그인
2. 회원가입
3. 결제 의도 생성
4. 거래 상태 관리
5. 사용자/가맹점 화면 API

Bank는 실제 자산 이동을 담당한다.

1. 계좌 잔액 변경
2. 지갑 잔액 변경
3. 원장 기록
4. 블록체인 트랜잭션 제출
5. 컨트랙트 호출

이렇게 나누면 실제 금융 시스템에서 흔히 볼 수 있는 구조와 비슷해진다. 플랫폼은 은행 또는 BaaS API를 호출하고, 은행은 실제 원장과 자산을 책임진다.

## 1.4 왜 FE가 블록체인을 직접 호출하지 않는가

FE가 블록체인을 직접 호출하면 다음 문제가 생긴다.

1. 개인키 관리가 어려워진다.
2. 사용자가 직접 서명해야 해서 UX가 복잡해진다.
3. 컨트랙트 주소, ABI, gas 정책이 클라이언트에 노출된다.
4. 실패/재시도/복구 로직을 브라우저가 감당해야 한다.
5. 사용자가 요청을 조작하기 쉽다.

이 프로젝트는 수탁형 지갑 구조를 사용한다. Bank 서버가 지갑 키를 생성하고 암호화해 보관하며, 서버가 검증 후 블록체인을 호출한다.

## 1.5 왜 RabbitMQ가 필요한가

블록체인 처리는 일반 DB 처리보다 느리고 불확실하다.

1. 노드 응답이 느릴 수 있다.
2. txHash는 받았지만 receipt가 늦게 나올 수 있다.
3. RPC 장애가 발생할 수 있다.
4. 컨트랙트 실행이 revert될 수 있다.

사용자 결제 API가 이 모든 과정을 기다리면 응답 시간이 길어진다. 그래서 Bank는 DB 원장 반영과 블록체인 요청 기록을 먼저 저장하고, RabbitMQ를 통해 블록체인 처리를 비동기로 넘긴다.

# 2장. 기능별 설명

## 2.1 회원가입

### 2.1.1 목적

회원가입은 사용자 또는 가맹점을 서비스에 등록하고, 결제에 필요한 계좌와 지갑을 준비하는 과정이다.

### 2.1.2 실제 흐름

```text
FE 회원가입 화면
 ↓
BE RegistrationController
 ↓
UserRegistrationService 또는 MerchantRegistrationService
 ↓
User/Merchant/Party 저장
 ↓
Bank API 호출
 ↓
BankAccount 생성
 ↓
BankWallet 생성
 ↓
BE Account/Wallet 저장
 ↓
응답
```

### 2.1.3 사용 기술

1. Spring MVC
2. DTO
3. Validation
4. JPA
5. BankClient
6. Redis Session

### 2.1.4 왜 이렇게 구현했는가

회원가입은 단순히 사용자 row만 저장하는 일이 아니다. 결제 서비스에서는 사용자가 결제할 수 있는 계좌와 지갑이 필요하다. 따라서 회원 등록 이후 Bank 서버에 계좌/지갑 생성을 요청한다.

### 2.1.5 다른 구현 방법

1. 회원가입 시 지갑을 만들지 않고 첫 결제 시 lazy 생성할 수 있다.
2. 계좌 인증을 외부 은행 API로 대체할 수 있다.
3. 회원과 지갑 생성 사이를 이벤트 기반 비동기로 분리할 수 있다.

### 2.1.6 면접 답변 예시

회원가입 과정에서 사용자 정보만 저장하지 않고, 결제에 필요한 계좌와 수탁형 지갑까지 생성했습니다. 플랫폼 서버는 사용자 도메인을 관리하고, 실제 계좌/지갑 생성은 Bank 서버 API를 통해 처리하도록 책임을 분리했습니다.

### 2.1.7 자소서 활용 포인트

회원가입과 동시에 결제에 필요한 계좌/지갑 리소스를 생성하도록 설계해, 이후 결제 플로우에서 필요한 선행 데이터를 안정적으로 준비했습니다.

## 2.2 로그인

### 2.2.1 목적

로그인은 사용자 또는 가맹점이 인증된 상태로 서비스를 이용하기 위한 기능이다.

### 2.2.2 실제 흐름

```text
FE 로그인 요청
 ↓
BE AuthController
 ↓
AuthService
 ↓
사용자/가맹점 검증
 ↓
Session 저장
 ↓
Redis Session 저장소 반영
 ↓
FE role 기반 홈 이동
```

### 2.2.3 사용 기술

1. Spring Security
2. Spring Session Data Redis
3. Servlet Session
4. Cookie 기반 인증
5. Route Guard

### 2.2.4 왜 Redis Session을 쓰는가

서버가 여러 대일 때 메모리 세션만 사용하면 문제가 생긴다.

```text
로그인 요청 -> WAS 1
다음 API 요청 -> WAS 2
WAS 2에는 세션 없음
```

Redis에 세션을 저장하면 여러 WAS가 같은 세션 저장소를 공유할 수 있다.

## 2.3 QR 결제

### 2.3.1 목적

사용자가 가맹점 QR을 스캔해 지역화폐로 결제하는 기능이다.

### 2.3.2 실제 흐름

```text
FE QR 스캔
 ↓
가맹점 ID 추출
 ↓
BE 결제 의도 생성
 ↓
PENDING Transaction 생성
 ↓
FE 결제 확인 화면
 ↓
PIN 입력
 ↓
BE 결제 실행
 ↓
Redis Lock
 ↓
멱등성 확인
 ↓
Bank 결제 API 호출
 ↓
Bank 원장 반영
 ↓
Outbox 저장
 ↓
RabbitMQ 발행
 ↓
Blockchain 결제 제출
```

### 2.3.3 사용 기술

1. React Router
2. QR scanner library
3. Spring MVC
4. Redis Lock
5. Redis Idempotency Store
6. JPA Transaction
7. Bank REST API
8. RabbitMQ
9. Web3j

### 2.3.4 왜 결제 의도를 먼저 만드는가

결제 버튼을 누르는 순간 바로 결제하지 않고 먼저 PENDING 거래를 만든다.

이유는 다음과 같다.

1. 결제 UUID를 서버가 발급해야 한다.
2. 같은 QR을 다시 스캔해도 기존 결제 의도를 재사용할 수 있다.
3. 결제 유효 시간을 관리할 수 있다.
4. 결제 실행 단계에서 멱등성 key로 사용할 수 있다.

### 2.3.5 면접 답변 예시

QR 결제는 먼저 결제 의도를 생성하고, 이후 PIN 검증 후 실행하는 2단계 구조로 만들었습니다. 이를 통해 결제 UUID를 서버가 발급하고, 같은 결제 요청이 반복되어도 Redis 멱등성 저장소와 DB 상태를 기준으로 중복 결제를 방지했습니다.

## 2.4 충전

### 2.4.1 목적

사용자의 은행 계좌 금액을 지역화폐 지갑 잔액으로 전환하는 기능이다.

### 2.4.2 실제 흐름

```text
FE 충전 금액 입력
 ↓
PIN 입력
 ↓
BE ChargeCommandService
 ↓
충전 멱등성 확인
 ↓
Bank charge API
 ↓
Bank 계좌 차감
 ↓
Bank 지갑 증가
 ↓
Blockchain mint 또는 ledger 기록
 ↓
응답
```

### 2.4.3 핵심 설계

충전은 돈이 늘어나는 작업이므로 중복 실행이 치명적이다. 따라서 transactionUuid와 Redis 멱등성 저장소, Bank 원장 상태를 통해 한 번만 처리되도록 한다.

## 2.5 환전

### 2.5.1 목적

사용자 또는 가맹점이 보유한 지역화폐를 은행 계좌 금액으로 되돌리는 기능이다.

### 2.5.2 실제 흐름

```text
FE 환전 요청
 ↓
BE ExchangeCommandService
 ↓
멱등성 확인
 ↓
Bank exchange API
 ↓
Bank 지갑 차감
 ↓
Bank 계좌 증가
 ↓
블록체인 burn/refund 요청
 ↓
UNKNOWN이면 reconcile 대상
```

### 2.5.3 왜 reconcile이 필요한가

Bank API 호출 중 timeout이 발생하면 실제 환전이 성공했는지 실패했는지 알 수 없다. 이 경우 바로 실패로 처리하면 실제로는 성공한 거래를 실패로 표시할 수 있다. 그래서 UNKNOWN 상태로 저장하고 나중에 조회 API로 최종 상태를 맞춘다.

## 2.6 결제 취소

### 2.6.1 목적

가맹점이 이미 성공한 결제를 취소해 금액을 사용자에게 되돌리는 기능이다.

### 2.6.2 실제 흐름

```text
가맹점 결제 상세
 ↓
취소 요청
 ↓
BE 원 결제 조회
 ↓
Cancel Lock 획득
 ↓
Cancel 멱등성 확인
 ↓
CANCEL Transaction 생성
 ↓
Bank cancel API
 ↓
가맹점 지갑 -> 사용자 지갑
 ↓
블록체인 취소 제출
```

### 2.6.3 왜 취소 거래를 별도로 저장하는가

원 결제 row만 수정하면 감사 추적이 어려워진다. 별도 CANCEL 거래를 남기면 원 결제와 취소 이력을 모두 보존할 수 있다.

## 2.7 거래 조회

### 2.7.1 목적

사용자와 가맹점이 결제, 충전, 환전, 취소 이력을 확인하는 기능이다.

### 2.7.2 사용 기술

1. JPA Repository
2. DTO Projection 또는 응답 DTO 변환
3. Cursor Pagination
4. 상태값 매핑
5. 날짜별 grouping

### 2.7.3 왜 cursor pagination을 사용하는가

offset pagination은 데이터가 많아질수록 뒤 페이지 조회 비용이 증가한다. 결제 내역은 최신순 조회가 많기 때문에 cursor 기반 페이지네이션이 더 적합하다.

## 2.8 가맹점 기능

가맹점은 QR 표시, 결제 내역 조회, 결제 취소, 정산/환전, 마이페이지 기능을 사용한다.

가맹점 기능의 핵심은 사용자 결제와 반대편에서 거래를 바라보는 것이다. 사용자에게는 지출이지만 가맹점에게는 매출이며, 정산 가능 금액 계산의 기준이 된다.

## 2.9 정산

정산은 가맹점이 받은 지역화폐를 은행 계좌 금액으로 전환하는 흐름이다. 기술적으로는 환전과 유사하지만, 주체가 가맹점이고 매출 내역/정산 계좌와 연결된다는 점이 다르다.

# 3장. 코드 문법 분석

## 3.1 `@RestController`

```java
@RestController
public class PaymentController {
}
```

`@RestController`는 해당 클래스가 REST API 요청을 받는 Controller임을 의미한다. 내부적으로 `@Controller`와 `@ResponseBody`가 합쳐진 형태다.

사용 이유는 메서드 반환값을 View 이름이 아니라 JSON 응답 body로 내려주기 위해서다.

## 3.2 `@PostMapping`

```java
@PostMapping("/payments")
```

HTTP POST 요청을 특정 메서드에 매핑한다.

POST는 보통 새로운 리소스를 생성하거나 상태를 변경할 때 사용한다. 결제 실행, 충전 실행, 회원가입처럼 상태가 바뀌는 요청에 적합하다.

## 3.3 `@GetMapping`

```java
@GetMapping("/payments/{id}")
```

HTTP GET 요청을 처리한다. 보통 조회 기능에서 사용한다.

GET은 서버 상태를 변경하지 않는 것이 원칙이다.

## 3.4 `@RequestBody`

```java
public ApiResponse<?> pay(@RequestBody PaymentExecuteRequest request)
```

HTTP 요청 body의 JSON을 Java 객체로 변환한다. 이때 Jackson이 JSON 필드와 Java record/class 필드를 매핑한다.

## 3.5 `@PathVariable`

```java
@GetMapping("/transactions/{transactionId}")
public Response get(@PathVariable Long transactionId)
```

URL 경로에 포함된 값을 메서드 파라미터로 받는다.

## 3.6 `@RequestParam`

```java
public Response get(@RequestParam Long institutionId)
```

Query String 값을 받는다.

```text
/bank-accounts/123?institutionId=1
```

## 3.7 `@Service`

```java
@Service
public class TransactionCommandService {
}
```

비즈니스 로직을 담당하는 Spring Bean으로 등록한다.

Controller는 요청/응답을 담당하고, 실제 판단과 상태 변경은 Service에서 수행한다.

## 3.8 `@Repository`

```java
@Repository
public interface TransactionRepository {
}
```

DB 접근 계층을 나타낸다. Spring Data JPA repository나 직접 구현 repository에 사용된다.

## 3.9 `@RequiredArgsConstructor`

```java
@RequiredArgsConstructor
public class PaymentService {
    private final PaymentRepository paymentRepository;
}
```

Lombok이 `final` 필드를 파라미터로 받는 생성자를 자동 생성한다.

Spring은 이 생성자를 통해 의존성을 주입한다.

```java
public PaymentService(PaymentRepository paymentRepository) {
    this.paymentRepository = paymentRepository;
}
```

이 코드를 직접 쓰지 않아도 되게 해준다.

## 3.10 DI

DI는 Dependency Injection, 의존성 주입이다.

서비스가 직접 repository를 `new`로 만들지 않고 Spring Container가 만들어 둔 Bean을 주입한다.

장점은 다음과 같다.

1. 테스트가 쉬워진다.
2. 객체 생성 책임이 분리된다.
3. 구현체 교체가 쉬워진다.

## 3.11 IoC

IoC는 Inversion of Control, 제어의 역전이다.

객체 생성과 생명주기를 개발자가 직접 관리하지 않고 Spring Container가 관리한다.

## 3.12 `@Transactional`

```java
@Transactional
public void execute() {
}
```

메서드 실행 중 DB 작업을 하나의 트랜잭션으로 묶는다.

중간에 RuntimeException이 발생하면 DB 변경을 rollback한다.

결제 시스템에서는 매우 중요하다.

```text
지갑 차감 성공
지갑 증가 실패
```

이런 상황이 발생하면 전체를 rollback해야 한다.

## 3.13 `Propagation.NOT_SUPPORTED`

```java
@Transactional(propagation = Propagation.NOT_SUPPORTED)
```

해당 메서드를 트랜잭션 없이 실행한다.

BE의 결제 실행에서 외부 Bank API 호출을 긴 DB 트랜잭션 안에 묶지 않기 위해 사용한다.

## 3.14 `Propagation.REQUIRES_NEW`

새로운 트랜잭션을 강제로 시작한다.

실패 기록을 남기거나 상태 전이를 별도 commit해야 할 때 사용한다.

## 3.15 `Optional<T>`

```java
Optional<Transaction> existing = repository.findByTransactionUuid(uuid);
```

값이 있을 수도 있고 없을 수도 있음을 타입으로 표현한다.

`null`을 직접 다루면 `NullPointerException` 위험이 커진다. Optional은 값이 없을 때의 처리를 명시하게 만든다.

## 3.16 `orElseThrow()`

```java
Transaction tx = repository.findById(id)
    .orElseThrow(() -> new BusinessException(PAYMENT_NOT_FOUND));
```

Optional에 값이 있으면 꺼내고, 없으면 예외를 던진다.

조회 실패를 명확하게 비즈니스 예외로 바꾸는 패턴이다.

## 3.17 Lambda

```java

```

람다는 익명 함수를 짧게 표현하는 Java 문법이다.

이 프로젝트에서는 retry 로직이나 lock 내부에서 실행할 작업을 전달할 때 사용된다.

Supplier<T>
```

```

컬렉션 데이터를 함수형 스타일로 처리한다.

## 3.20 `filter`

# 4장. 핵심 코드 로직 분석

## 4.1 `executePayment()` 로직

결제 실행의 핵심 순서는 다음과 같다.

```text
1. Redis Lock 획득
2. 거래 조회
3. 권한 검증
4. PIN 검증
5. 상태 검증
6. 멱등성 확인
7. PROCESSING 저장
8. Bank 호출
9. 결과 분류
10. SUCCESS/FAILED/UNKNOWN 반영
11. 멱등성 snapshot 저장
12. 응답
```

## 4.2 왜 Lock을 먼저 잡는가

사용자가 결제 버튼을 빠르게 두 번 누르면 같은 `transactionUuid`로 요청이 동시에 들어올 수 있다.

락이 없으면 다음 문제가 생긴다.

```text
요청 A: 아직 결제 안 됨 확인
요청 B: 아직 결제 안 됨 확인
요청 A: Bank 결제 호출
요청 B: Bank 결제 호출
```

결과적으로 중복 결제가 발생할 수 있다.

## 4.3 왜 상태 검증이 필요한가

결제는 아무 상태에서나 실행되면 안 된다.

1. PENDING이면 실행 가능
2. SUCCESS면 이미 성공
3. FAILED면 이미 실패
4. EXPIRED면 만료
5. PROCESSING이면 처리 중
6. UNKNOWN이면 복구 대상

상태 검증이 없으면 성공한 결제를 다시 실행하거나, 만료된 결제를 실행할 수 있다.

## 4.4 왜 requestHash를 만드는가

같은 `transactionUuid`라도 요청 내용이 다르면 중복 요청이 아니라 충돌이다.

```text
첫 요청: uuid=A, amount=10000, merchant=1
두 번째 요청: uuid=A, amount=50000, merchant=1
```

이 경우 기존 응답을 반환하면 안 되고 `IDEMPOTENCY_CONFLICT`로 막아야 한다.

## 4.5 왜 Bank 호출 결과를 분류하는가

Bank 호출 결과는 단순 성공/실패가 아니다.

1. 명확한 성공
2. 명확한 실패
3. 결과 불명확

네트워크 timeout은 결과 불명확이다. Bank가 실제로 처리했는지 알 수 없기 때문이다.

## 4.6 `callBankWithRetry()` 로직

Bank 호출은 다음 순서로 처리된다.

```text
1차 호출
 ↓
성공이면 SUCCESS
 ↓
재시도 불가능한 오류면 FAILED
 ↓
재시도 가능한 오류면 짧게 대기
 ↓
2차 호출
 ↓
성공이면 SUCCESS
 ↓
또 재시도 가능한 오류면 UNKNOWN
 ↓
명확한 오류면 FAILED
```

이 방식은 일시적인 충돌이나 네트워크 문제를 한 번 완화하면서도, 무한 재시도로 요청 스레드를 오래 붙잡지 않는다.

## 4.7 `recoverPayment()` 로직

UNKNOWN 상태는 복구가 필요하다.

```text
UNKNOWN 거래 조회
 ↓
Bank 상태 조회
 ↓
SUCCESS면 BE도 SUCCESS
 ↓
FAILED면 BE도 FAILED
 ↓
PROCESSING이면 다음 주기 재시도
 ↓
NOT_FOUND면 FAILED 보정
```

복구 로직이 없으면 UNKNOWN 거래가 영원히 남는다.

## 4.8 Outbox 발행 로직

Bank의 outbox 발행은 다음 순서다.

```text
NEW outbox 조회
 ↓
RabbitMQ publish
 ↓
성공하면 SENT
 ↓
실패하면 retryCount 증가
 ↓
한도 초과 시 FAILED
```

## 4.9 Blockchain consumer 로직

```text
메시지 수신
 ↓
BlockchainLedger 조회
 ↓
이미 SUCCESS/FAILED면 무시
 ↓
txHash 있으면 재사용
 ↓
txHash 없으면 컨트랙트 submit
 ↓
SUBMITTED 저장
 ↓
receipt 조회
 ↓
SUCCESS/FAILED 저장
```

핵심은 txHash 재사용이다. consumer가 죽었다가 다시 실행되어도 같은 블록체인 거래를 중복 제출하지 않도록 한다.

# 5장. 설계 이유

## 5.1 왜 Redis Lock을 썼는가

결제 버튼은 동시에 여러 번 눌릴 수 있다. 서버가 여러 대라면 Java의 `synchronized`로는 막을 수 없다.

Redis는 여러 WAS가 공유하는 중앙 저장소이므로 분산 락을 구현할 수 있다.

## 5.2 왜 DB Lock도 필요한가

Redis는 1차 방어선이다. 하지만 Redis 장애, TTL 만료, 네트워크 지연 같은 상황이 있을 수 있다.

실제 잔액 변경은 DB가 최종 책임을 져야 한다. 그래서 Bank는 row lock과 unique constraint를 사용한다.

## 5.3 왜 Outbox를 사용했는가

다음 상황을 생각해보자.

```text
DB 원장 저장 성공
 ↓
RabbitMQ 발행 직전 서버 장애
```

Outbox가 없으면 블록체인 동기화 메시지가 유실된다.

Outbox를 사용하면 DB 트랜잭션 안에 메시지 발행 예정 기록을 함께 저장한다. 이후 스케줄러가 NEW outbox를 다시 찾아 발행한다.

## 5.4 왜 UNKNOWN 상태가 있는가

외부 API 호출에서 timeout이 발생하면 실제 성공 여부를 모른다.

```text
BE -> Bank 요청 전송
Bank 처리 성공
응답 중 네트워크 timeout
BE는 응답 못 받음
```

이때 BE가 FAILED로 저장하면 실제 성공 거래와 불일치한다. 따라서 UNKNOWN으로 저장하고 나중에 Bank 상태 조회로 복구한다.

## 5.5 왜 멱등성이 필요한가

결제 요청은 네트워크 문제로 재전송될 수 있다. 사용자가 버튼을 여러 번 누를 수도 있다.

멱등성이 없으면 같은 결제가 여러 번 실행된다.

멱등성이 있으면 같은 요청에 대해 첫 처리 결과를 재사용한다.

## 5.6 왜 상태 머신이 필요한가

결제는 단순 CRUD가 아니다. 각 상태에서 허용되는 다음 행동이 다르다.

상태 머신이 없으면 다음 문제가 생긴다.

1. 이미 성공한 결제를 다시 실행
2. 실패한 결제를 다시 성공 처리
3. 만료된 결제 실행
4. 처리 중 결제 중복 실행

상태 머신은 거래의 생명주기를 명확하게 제한한다.

## 5.7 왜 RabbitMQ인가

RabbitMQ는 작업 큐 기반 비동기 처리에 적합하다.

이 프로젝트에서는 블록체인 제출 작업을 순차적으로 처리하고, 실패 시 retry/DLQ로 보낼 수 있으면 충분하다. 대규모 이벤트 스트리밍보다는 명확한 작업 전달이 중요하므로 RabbitMQ가 적합하다.

Kafka는 대용량 로그 스트리밍과 이벤트 재처리에 강하지만, 운영 복잡도가 더 크다.

## 5.8 왜 Web3j인가

서버가 Java/Spring Boot 기반이기 때문에 Java에서 Ethereum/Besu JSON-RPC와 스마트 컨트랙트를 호출하기 쉬운 Web3j를 사용한다.

# 6장. 면접 대비

## 6.1 Redis를 왜 사용했나요?

좋은 답변:

Redis는 세션 공유, 분산 락, 멱등성 저장소, rate limit에 사용했습니다. 특히 결제 요청은 여러 WAS에서 동시에 들어올 수 있기 때문에 Redis `SET NX` 기반 분산 락으로 같은 transactionUuid의 중복 실행을 막았습니다. 또한 멱등성 record에 requestHash와 responseSnapshot을 저장해 같은 요청이 재시도되면 기존 결과를 반환하도록 했습니다.

추가 질문:

1. Redis가 죽으면 어떻게 되나요?
2. Redis Lock만으로 충분한가요?
3. Redisson을 쓰지 않은 이유는 무엇인가요?

답변 포인트:

Redis는 1차 방어선이고, Bank DB unique constraint와 row lock이 최종 방어선이다.

## 6.2 RabbitMQ를 왜 사용했나요?

좋은 답변:

블록체인 처리는 receipt 확인까지 시간이 오래 걸리고 RPC 장애 가능성이 있어 API 요청 경로에서 분리했습니다. Bank 서버는 DB 원장과 outbox를 먼저 저장하고, RabbitMQ를 통해 블록체인 제출 작업을 비동기로 처리했습니다.

## 6.3 Kafka가 아니라 RabbitMQ를 선택한 이유는?

좋은 답변:

이 프로젝트에서는 대규모 이벤트 로그 스트리밍보다 결제 후 블록체인 제출이라는 작업 큐 성격이 강했습니다. RabbitMQ는 routing, ack/nack, retry, DLQ 구성이 단순하고 작업 처리 모델에 적합해 선택할 수 있습니다.

## 6.4 Outbox Pattern이 무엇인가요?

좋은 답변:

DB 변경과 메시지 발행을 원자적으로 묶기 위한 패턴입니다. 실제 메시지를 바로 MQ에 발행하지 않고, 같은 DB 트랜잭션 안에 outbox 테이블에 발행 예정 메시지를 저장합니다. 이후 별도 scheduler가 outbox를 읽어 MQ에 발행합니다. 이렇게 하면 DB 저장 성공 후 MQ 발행 실패로 메시지가 유실되는 문제를 줄일 수 있습니다.

## 6.5 멱등성이 무엇인가요?

좋은 답변:

같은 요청이 여러 번 들어와도 결과가 한 번 처리된 것과 동일하게 유지되는 성질입니다. 결제에서는 네트워크 재시도나 버튼 중복 클릭으로 같은 요청이 반복될 수 있으므로 필수입니다. 이 프로젝트에서는 transactionUuid와 requestHash를 기준으로 Redis에 처리 상태와 응답 snapshot을 저장했습니다.

## 6.6 UNKNOWN 상태는 왜 필요한가요?

좋은 답변:

외부 Bank API 호출에서 timeout이 발생하면 실제 처리 여부를 알 수 없습니다. 이때 실패로 확정하면 실제 성공한 거래와 불일치할 수 있습니다. 그래서 UNKNOWN 상태로 저장한 뒤 recovery scheduler가 Bank 상태 조회 API를 호출해 SUCCESS 또는 FAILED로 확정합니다.

## 6.7 `@Transactional`은 왜 사용했나요?

좋은 답변:

잔액 차감, 잔액 증가, 거래 상태 변경처럼 함께 성공하거나 함께 실패해야 하는 DB 작업을 하나의 트랜잭션으로 묶기 위해 사용했습니다. 결제 시스템에서는 일부만 반영되면 금액 불일치가 발생하기 때문에 원자성이 중요합니다.

## 6.8 비관적 락과 낙관적 락 차이는?

비관적 락은 충돌이 날 것으로 보고 먼저 row를 잠근다. 낙관적 락은 충돌이 적다고 보고 version으로 나중에 충돌을 감지한다.

결제처럼 잔액이 직접 바뀌고 충돌 비용이 큰 경우 비관적 락이 더 직관적일 수 있다.

## 6.9 왜 Controller에 비즈니스 로직을 넣지 않았나요?

Controller는 HTTP 요청/응답 변환과 인증 주체 전달만 담당해야 한다. 비즈니스 규칙은 Service에 있어야 테스트가 쉽고, 책임이 분리된다.

## 6.10 Web3j는 어떤 역할인가요?

Java 서버에서 블록체인 JSON-RPC를 호출하고 스마트 컨트랙트 함수를 실행하기 위한 라이브러리다. 이 프로젝트에서는 결제, 취소, 환전 관련 컨트랙트 함수를 호출하고 txHash와 receipt를 확인하는 데 사용했다.

# 11장. 기술별 핵심 요약

## 11.1 Spring Boot

이 프로젝트에서 Spring Boot는 API 서버의 기반이다. Controller는 요청을 받고, Service는 비즈니스 로직을 처리하며, Repository는 DB 접근을 담당한다.

## 11.2 JPA

JPA는 Java 객체와 DB 테이블을 매핑한다. Entity는 DB row와 연결되고, Repository는 CRUD와 query를 담당한다.

## 11.3 Redis

Redis는 빠른 key-value 저장소다. 이 프로젝트에서는 세션, 락, 멱등성, rate limit에 사용된다.

## 11.4 RabbitMQ

RabbitMQ는 메시지 큐다. Bank의 블록체인 제출 작업을 비동기로 처리하기 위해 사용된다.

## 11.5 Outbox

Outbox는 DB 저장과 메시지 발행 사이의 유실을 줄이는 패턴이다.

## 11.6 Web3j

Web3j는 Java에서 블록체인 노드와 통신하기 위한 라이브러리다.

## 11.7 React

React는 FE 화면을 구성한다. 이 프로젝트에서는 사용자와 가맹점의 모바일 앱 형태 UI를 담당한다.

## 11.8 nginx

nginx는 FE 정적 파일을 서빙하고 `/api` 요청을 BE로 프록시한다. React Router를 위해 SPA fallback 설정도 포함한다.
