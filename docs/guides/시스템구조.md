# 한강페이 시스템 구조 가이드

## 0. 모노레포 전체 개요

한강페이는 CBDC/지역화폐 결제 흐름을 모사한 모노레포 프로젝트다. 사용자는 계좌 기반으로 지역화폐를 충전하고, 가맹점 QR을 통해 결제하며, 가맹점은 결제 내역 조회와 정산/환전을 수행한다. 전체 구조는 프론트엔드 SPA, 플랫폼 API 서버, 은행/BaaS 서버, 블록체인 네트워크/컨트랙트, nginx 배포 설정으로 나뉜다.

```text
hangang-pay/
├─ hangang-pay-bank/   # 은행/BaaS 서버: 계좌, 지갑, 원장, 블록체인 제출/동기화
├─ hangang-pay-be/     # 플랫폼 API 서버: 인증, 회원, 결제 의도/실행, 충전, 환전, 가맹점 API
├─ hangang-pay-fe/     # React SPA: 사용자/가맹점 모바일 UI
├─ nginx/              # 정적 FE 서빙 및 BE 프록시 설정
├─ hangang-pay-bc/     # Besu/Hardhat/Solidity 기반 블록체인 구성
├─ docs/               # 테스트 데이터, 제출 자료, 이미지/시연 자료
├─ README.md
├─ SUBMIT.md
└─ CLAUDE.md / AGENTS.md
```

런타임 상호작용은 `FE -> BE -> Bank -> Blockchain` 흐름을 기본으로 한다. FE는 `/api/v1` REST API를 호출하고, BE는 인증/세션/도메인 검증 및 거래 상태를 관리한 뒤 Bank API를 호출한다. Bank는 실제 계좌/지갑 원장 변경과 블록체인 제출 책임을 갖는다. 블록체인 제출은 RabbitMQ와 Outbox 패턴을 통해 비동기로 처리된다.

기술 스택은 Java 17, Spring Boot 3.5.x, Spring Data JPA, MySQL, Redis, RabbitMQ, Web3j, Hardhat, Solidity, React 19, TypeScript, Vite, TanStack Query, Zustand, Tailwind CSS, nginx, Sentry, Prometheus/Micrometer, Alloy/Grafana 계열로 구성되어 있다.

## 1. `hangang-pay-bank` 폴더

### 1.1 역할과 책임

`hangang-pay-bank`는 은행/BaaS 서버다. 플랫폼 서버인 `hangang-pay-be`가 직접 블록체인과 은행 원장을 만지지 않도록, 계좌/지갑/원장/블록체인 제출 책임을 별도 서비스로 분리했다.

주요 책임은 다음과 같다.

1. 은행 기관, 은행 계좌, 수탁형 지갑 관리
2. 충전, 결제, 결제 취소, 환전 처리
3. 지갑 원장과 계좌 원장 기록
4. 블록체인 트랜잭션 제출 및 영수증 확인
5. RabbitMQ 기반 비동기 블록체인 동기화
6. 블록체인 outbox, retry, DLQ, reconcile 관리
7. Web3j 기반 스마트 컨트랙트 호출

### 1.2 주요 패키지 구조

```text
hangang-pay-bank/src/main/java/family/fisa/hangangpaybank/
├─ domain/
│  ├─ institution/       # 은행 기관, 계좌, 수탁형 지갑, 컨트랙트 메타데이터
│  ├─ ledger/            # 계좌 원장, 지갑 원장
│  ├─ transaction/       # 충전/결제/취소/환전 비즈니스 로직
│  ├─ blockchain/        # Web3j 컨트랙트 호출, txHash/receipt, 블록체인 원장
│  └─ blockchainoutbox/  # Outbox, 순서 보장, MQ 발행
├─ infra/
│  └─ mq/rabbit/         # RabbitMQ 설정, publisher, listener
└─ global/
   ├─ config/            # JPA 설정
   ├─ code/              # 공통 성공/오류 코드
   ├─ exception/         # BusinessException, GlobalExceptionHandler
   ├─ logging/           # MDC requestId 로깅
   └─ response/          # ApiResponse
```

### 1.3 기관/계좌/지갑 도메인

`domain/institution`은 은행 시스템의 기준 정보를 다룬다.

1. `Institution`: 은행/기관 정보
2. `BankAccount`: 실제 계좌 잔액과 계좌번호
3. `BankWallet`: 블록체인 지갑 주소와 암호화된 private key
4. `Contract`: 배포된 스마트 컨트랙트 주소
5. `ContractArtifact`: ABI/바이트코드 등 컨트랙트 산출물

수탁형 지갑 구조를 사용한다. 사용자가 개인키를 직접 보관하지 않고 Bank 서버가 EC key pair를 생성한 뒤 private key를 암호화해 저장한다. BE와 FE는 지갑 주소만 사용하고, 실제 서명과 컨트랙트 호출은 Bank가 수행한다.

`WalletKeyCipher`는 지갑 개인키 암호화/복호화 책임을 갖는다. 결제, 취소, 환전, 충전 시 Web3j가 사용할 credentials를 만들기 위해 이 키를 복호화한다.

### 1.4 원장 도메인

`domain/ledger`는 실제 금액 이동의 기록을 담당한다.

1. `AccountLedger`: 은행 계좌 잔액 변동 기록
2. `WalletLedger`: 지역화폐 지갑 잔액 변동 기록
3. `LedgerType`: CHARGE, PAYMENT, CANCEL, EXCHANGE 등 거래 종류
4. `LedgerStatus`: SUCCESS, FAILED 등 원장 상태
5. `WalletLedgerDirection`: 입금/출금 방향

결제 시스템에서 원장은 단순 로그가 아니라 재처리와 검증의 기준이다. Bank 서버는 실패 상황에서도 실패 원장을 남겨 추적 가능하게 만들고, 블록체인 상태와 DB 상태가 어긋났을 때 reconcile 기준으로 활용한다.

### 1.5 충전 로직

충전은 사용자의 은행 계좌 금액을 차감하고 지역화폐 토큰을 발행하는 흐름이다.

세부 흐름은 다음과 같다.

1. BE가 Bank의 `/api/v1/transactions/charge`를 호출한다.
2. Bank는 `TransactionCommandService.charge()`에서 기존 `transactionUuid` 처리 여부를 먼저 확인한다.
3. 이미 SUCCESS면 기존 성공 응답을 반환한다.
4. PENDING/SUBMITTED면 중복 처리 중으로 보고 예외를 반환한다.
5. FAILED면 이미 실패한 거래로 보고 재처리를 막는다.
6. 신규 요청이면 계좌와 지갑 상태를 검증한다.
7. `BlockchainLedger`를 PENDING으로 선점한다.
8. 계좌 원장, 지갑 원장, 블록체인 mint 요청을 기록한다.
9. 성공 시 ledger를 SUCCESS로 확정하고, 실패 시 실패 원장을 저장한다.

이 로직은 충전 요청의 멱등성을 `transactionUuid`와 `BlockchainLedger` 상태로 보장한다. 충전은 토큰 발행이 포함되므로, 같은 UUID에 대해 두 번 mint되지 않도록 PENDING 선점이 중요하다.

### 1.6 결제 로직

결제는 사용자 지갑에서 가맹점 지갑으로 지역화폐를 이동시키는 흐름이다.

핵심 클래스는 다음과 같다.

1. `TransactionCommandService.payment()`
2. `PaymentExecutionService`
3. `PaymentStateWriter`
4. `PaymentBlockchainSyncHandler`
5. `ContractCallService.submitPayment()`

Bank 내부 처리 흐름은 다음과 같다.

1. BE가 `transactionUuid`, 사용자 지갑 주소, 가맹점 지갑 주소, 금액을 보낸다.
2. Bank는 원장 중복 여부와 잔액을 검증한다.
3. 지갑 잔액을 DB 트랜잭션 안에서 차감/증가한다.
4. `BlockchainLedger`를 PENDING으로 저장한다.
5. `BlockchainOutbox`에 블록체인 동기화 메시지를 NEW 상태로 저장한다.
6. API 응답은 DB 반영 후 반환한다.
7. 별도 스케줄러가 outbox를 RabbitMQ로 발행한다.
8. RabbitMQ consumer가 스마트 컨트랙트 `pay`를 호출한다.
9. txHash 확보 즉시 SUBMITTED로 저장한다.
10. receipt 확인 후 SUCCESS 또는 FAILED로 확정한다.

즉, 사용자 응답 경로에서는 DB 원장 반영까지 빠르게 처리하고, 블록체인 확정은 비동기로 진행한다.

### 1.7 결제 취소 로직

결제 취소는 원 결제와 반대 방향의 지갑 이동이다.

1. 원 결제 거래를 조회한다.
2. 취소 가능 상태인지 검증한다.
3. 취소 거래용 `transactionUuid`를 별도로 사용한다.
4. 가맹점 지갑에서 사용자 지갑으로 금액을 되돌린다.
5. 지갑 원장에 CANCEL 타입을 기록한다.
6. outbox에 cancel payload를 저장한다.
7. 블록체인 consumer가 `submitCancelPayment()`를 통해 컨트랙트에 반대 방향 transfer를 제출한다.

현재 구조는 부분 취소보다 전체 취소 중심이다. 부분 취소를 확장하려면 원 결제 금액, 누적 취소 금액, 남은 취소 가능 금액, 다중 취소 이력 검증이 추가로 필요하다.

### 1.8 환전 로직

환전은 사용자 또는 가맹점이 보유한 지역화폐를 은행 계좌 금액으로 되돌리는 흐름이다.

주요 클래스는 다음과 같다.

1. `ExchangeOrchestrator`
2. `ExchangeExecutionService`
3. `ExchangeStateWriter`
4. `ExchangeQueryService`
5. `ExchangeBlockchainSyncHandler`

환전은 토큰 burn 또는 refund 성격의 컨트랙트 호출과 계좌 입금 처리가 함께 필요하다. Bank는 DB 원장 상태와 블록체인 원장을 분리하여, 블록체인 제출이 지연되거나 실패해도 추적 가능한 상태를 유지한다.

### 1.9 Outbox 패턴

`domain/blockchainoutbox`는 블록체인 요청을 안정적으로 MQ에 전달하기 위한 Outbox 구현이다.

핵심 클래스는 다음과 같다.

1. `BlockchainOutboxSyncRequester`
2. `BlockchainOutboxPublisherScheduler`
3. `BlockchainOrderingSequenceAllocator`
4. `BlockchainSyncHandlerRegistry`
5. `BlockchainOutboxRepository`

처리 순서는 다음과 같다.

1. 결제/취소/환전 비즈니스 트랜잭션 안에서 `BlockchainLedger(PENDING)`를 저장한다.
2. 같은 트랜잭션 안에서 `BlockchainOutbox(NEW)`를 저장한다.
3. 스케줄러가 NEW outbox를 batch로 조회한다.
4. RabbitMQ로 메시지를 publish한다.
5. publish 성공 시 outbox를 SENT로 바꾼다.
6. publish 실패 시 retry count를 증가시키고, 한도를 넘으면 FAILED로 바꾼다.

이 패턴을 사용한 이유는 DB 반영과 MQ 발행 사이의 장애를 줄이기 위해서다. 결제 DB 변경만 성공하고 메시지 발행 전에 서버가 죽어도, outbox에 NEW 레코드가 남아 있기 때문에 다음 스케줄에서 다시 발행할 수 있다.

### 1.10 RabbitMQ 비동기 처리

`infra/mq/rabbit`에는 RabbitMQ 설정과 publisher/listener가 있다.

1. `RabbitMqConfig`: exchange, queue, binding, retry/DLQ 설정
2. `RabbitBlockchainSyncMessagePublisher`: outbox 메시지 발행
3. `RabbitBlockchainSyncMessageListener`: 메시지 수신 후 handler 호출

RabbitMQ는 블록체인 I/O를 HTTP 요청 경로에서 분리하는 역할을 한다. 블록체인 노드 응답 지연, receipt timeout, 일시적인 RPC 장애가 발생해도 사용자 결제 API 자체가 블록체인 확정까지 기다리지 않는다.

### 1.11 블록체인 동기화 처리

`BlockchainSyncProcessor`는 RabbitMQ 메시지를 받아 실제 Web3j 컨트랙트 호출을 수행한다.

핵심 알고리즘은 다음과 같다.

1. 메시지 payload를 타입별 DTO로 역직렬화한다.
2. `BlockchainLedger`를 조회한다.
3. 이미 SUCCESS/FAILED인 terminal 상태면 메시지를 무시한다.
4. txHash가 이미 있으면 재제출하지 않고 기존 txHash를 재사용한다.
5. txHash가 없으면 컨트랙트 함수를 호출하고 즉시 SUBMITTED로 저장한다.
6. txHash로 receipt를 기다린다.
7. receipt가 성공이면 SUCCESS, 실패면 FAILED로 저장한다.
8. RPC 실패나 receipt timeout은 retryable로 보고 예외를 다시 던져 DLQ/retry 흐름에 맡긴다.
9. `AlreadyProcessed`는 컨트랙트에서 이미 처리된 거래로 보고 SUCCESS 계열로 보정한다.

이 구조에서 중요한 점은 `SUBMITTED` 체크포인트다. 컨트랙트 제출 직후 txHash를 DB에 저장해두면, consumer가 중간에 죽어도 같은 트랜잭션을 다시 제출하지 않고 기존 txHash의 receipt만 확인할 수 있다.

### 1.12 순서 보장 알고리즘

`BlockchainOrderingSequenceAllocator`는 ordering key별 시퀀스를 발급한다. ordering key는 보통 지갑 주소다.

같은 지갑 주소에서 발생한 블록체인 요청은 순서가 중요하다. 예를 들어 같은 지갑에서 결제와 취소가 동시에 제출되면 nonce 또는 잔액 순서 문제가 발생할 수 있다. 따라서 ordering key를 기준으로 seqNo를 부여하고, 메시지 처리/발행 시 순서 추적이 가능하도록 한다.

### 1.13 DB 비관적 락과 멱등성

Bank는 실제 잔액을 바꾸는 최종 방어선이므로 DB 제약과 락을 적극 사용한다.

1. `transactionUuid` 계열 unique constraint로 중복 원장 저장을 막는다.
2. 지갑/계좌 잔액 변경 구간은 `PESSIMISTIC_WRITE` 성격의 row lock을 사용한다.
3. 같은 지갑을 동시에 수정할 때 lost update를 막는다.
4. 결제/취소/환전 실패 시 실패 원장을 남겨 재처리 가능성을 유지한다.

분산 시스템에서 Redis나 MQ가 일시적으로 실패할 수 있으므로, Bank의 DB unique constraint는 마지막 중복 방어선 역할을 한다.

### 1.14 Web3j와 스마트 컨트랙트 호출

`domain/blockchain/service/ContractCallService`는 Web3j를 사용해 스마트 컨트랙트를 호출한다.

주요 호출은 다음과 같다.

1. `submitPayment`: 사용자 지갑에서 가맹점 지갑으로 지역화폐 강제 이체
2. `submitCancelPayment`: 결제 취소 방향 이체
3. `submitRefund`: 환전 시 토큰 burn/refund 계열 처리
4. `waitForReceiptByHash`: txHash 기준 receipt 확인

`BlockchainTransactionKeyConverter`는 UUID를 컨트랙트가 다루는 `bytes32` 형태로 변환한다. 이 값은 컨트랙트의 `processedTx` 같은 중복 처리 방지 구조와 연결된다.

### 1.15 관측성

Bank는 다음 관측성 기술을 사용한다.

1. Spring Boot Actuator
2. Micrometer Prometheus registry
3. Sentry Spring Boot starter
4. Sentry Logback
5. MDC 기반 requestId 로깅
6. Alloy 설정 파일

이를 통해 API 지표, JVM 지표, 오류 추적, 로그 상관관계를 확인할 수 있다.

## 2. `hangang-pay-be` 폴더

### 2.1 역할과 책임

`hangang-pay-be`는 사용자와 가맹점이 직접 호출하는 플랫폼 API 서버다. 인증, 세션, 회원가입, 계좌 연결, 지갑 조회, QR 기반 결제, 충전, 환전, 결제 취소, 거래 내역 조회를 담당한다.

BE는 실제 계좌/지갑 원장을 직접 변경하지 않고 `client/bank`를 통해 Bank API를 호출한다. 대신 사용자 경험과 거래 생명주기를 관리한다. 특히 결제 의도 생성, 결제 실행, 멱등성, 분산 락, rate limit, UNKNOWN 복구, 만료 스케줄링이 BE의 핵심 로직이다.

### 2.2 주요 패키지 구조

```text
hangang-pay-be/src/main/java/family/fisa/hangangpay/
├─ auth/              # 로그인, 로그아웃, 회원가입, SMS/계좌 인증
```

### 2.3 인증과 세션

`auth` 패키지는 인증과 회원가입 흐름을 담당한다.

1. `AuthController`: 로그인/로그아웃
2. `RegistrationController`: 사용자/가맹점 회원가입
3. `VerificationController`: SMS/계좌 인증
4. `AuthService`: 로그인 인증 처리
5. `UserRegistrationService`: 사용자 가입 처리
6. `MerchantRegistrationService`: 가맹점 가입 처리
7. `VerificationService`: 인증 코드 발급/검증

Spring Security와 Spring Session Data Redis를 사용한다. 세션은 Redis에 저장되므로 여러 WAS 인스턴스에서도 동일한 로그인 상태를 공유할 수 있다. `SessionAuthenticationFilter`는 세션 attribute에서 partyId/role 등을 읽어 인증 컨텍스트를 구성한다.

### 2.4 Party/User/Merchant 구조

`party`는 사용자와 가맹점의 공통 상위 개념이다.

1. `Party`: USER/MERCHANT 공통 식별자
2. `PartyType`: USER, MERCHANT
3. `User`: 사용자 상세 정보
4. `Merchant`: 가맹점 상세 정보, 사업자 정보, 정산 관련 정보

이 구조를 사용하면 계좌, 지갑, 거래처럼 사용자와 가맹점 모두에게 필요한 기능을 `partyId` 기준으로 공통 처리할 수 있다.

### 2.5 계좌와 지갑

`account`는 플랫폼에 연결된 은행 계좌 정보를 관리한다. 실제 은행 계좌 생성/조회는 Bank 서버에 위임하고, BE는 사용자/가맹점과 계좌 연결 관계를 관리한다.

`wallet`은 사용자/가맹점의 서비스 지갑 주소와 잔액 조회를 담당한다. 실제 지갑 발급과 키 관리는 Bank에서 수행한다. BE는 지갑 주소와 Bank 응답을 바탕으로 화면에 필요한 잔액 정보를 제공한다.

### 2.6 BankClient 연동

`client/bank/BankClientImpl`은 BE와 Bank 서버 사이의 REST adapter다.

주요 API 호출은 다음과 같다.

1. 은행 계좌 생성/조회
2. 은행 지갑 생성/조회
3. 충전 요청
4. 결제 요청
5. 결제 취소 요청
6. 환전 요청
7. 거래 상태 조회
8. 블록체인 원장 조회

`RestClient`를 사용하고, Bank의 `ApiResponse<T>` 구조에서 `result`를 추출한다. Bank가 반환한 에러 코드는 BE 도메인 에러 코드로 매핑하거나, 매핑되지 않은 경우 외부 Bank 에러로 감싼다.

### 2.7 결제 의도 생성

결제는 바로 실행하지 않고 먼저 `PaymentIntent`를 만든다.

핵심 클래스는 `TransactionCommandService.createPaymentIntent()`다.

처리 흐름은 다음과 같다.

1. `PaymentRateLimiter.checkIntentRateLimit()`로 결제 의도 생성 요청량을 제한한다.
2. 사용자 party, 가맹점, 사용자 지갑, 가맹점 지갑을 조회한다.
3. 같은 사용자/가맹점/금액 조합의 살아있는 PENDING 결제가 있는지 찾는다.
4. 있으면 기존 결제 의도를 재사용한다.
5. 없으면 fingerprint를 만들고 Redis dedup store에 예약한다.
6. 서버가 `transactionUuid`를 발급한다.
7. `Transaction.forPayment()`로 PENDING 거래를 저장한다.
8. FE에는 결제 의도와 만료 시간을 반환한다.

결제 의도 TTL은 코드상 10분이다. 같은 QR을 다시 스캔하거나 결제 화면에 재진입해도 살아있는 PENDING 거래가 있으면 새 거래를 만들지 않고 기존 거래를 반환한다.

### 2.8 결제 실행

결제 실행은 `TransactionCommandService.executePayment()`에서 시작한다.

중요한 특징은 다음과 같다.

1. 외부 Bank 호출을 DB 트랜잭션 안에 오래 묶지 않기 위해 `Propagation.NOT_SUPPORTED`를 사용한다.
2. `PaymentLockManager.withTransactionLock()`으로 `transactionUuid` 기준 Redis 분산 락을 획득한다.
3. `PaymentExecutionStateWriter.prepareExecution()`에서 결제 PIN, 거래 상태, 권한을 검증하고 PROCESSING으로 전환한다.
4. 이미 멱등성 snapshot이 있으면 즉시 기존 응답을 반환한다.
5. Bank 결제 API를 호출한다.
6. 응답을 SUCCESS, UNKNOWN, TERMINAL_FAILED로 분류한다.
7. SUCCESS면 거래를 성공 확정하고 snapshot을 Redis에 저장한다.
8. UNKNOWN이면 후속 복구 스케줄러가 확인할 수 있도록 UNKNOWN 상태로 저장한다.
9. 명시적 실패면 FAILED로 저장하고 비즈니스 예외를 던진다.

### 2.9 결제 상태 머신

BE의 `TransactionStatus`는 거래 생명주기를 표현한다.

주요 상태는 다음과 같다.

1. `PENDING`: 결제 의도 생성, 아직 Bank 실행 요청 전
2. `PROCESSING`: Bank 실행 요청을 보냈거나 처리 중
3. `SUCCESS`: 최종 성공
4. `FAILED`: 최종 실패
5. `UNKNOWN`: Bank 호출 결과가 불명확함
6. `EXPIRED`: 결제 의도 유효 시간이 만료됨

상태 전이는 다음과 같다.

```text
PENDING -> PROCESSING -> SUCCESS
PENDING -> PROCESSING -> FAILED
PENDING -> PROCESSING -> UNKNOWN -> SUCCESS
PENDING -> PROCESSING -> UNKNOWN -> FAILED
PENDING -> EXPIRED
```

`UNKNOWN`을 별도로 두는 이유는 외부 Bank 호출에서 timeout이나 네트워크 장애가 발생했을 때 실제 처리 여부를 알 수 없기 때문이다. 이때 곧바로 FAILED로 확정하면 실제로는 성공한 결제를 실패로 안내할 수 있다. 따라서 Bank 상태 조회를 통해 나중에 확정한다.

### 2.10 결제 복구 로직

`recoverPayment()`와 `UnknownPaymentRecoveryScheduler`는 UNKNOWN/PROCESSING 거래를 복구한다.

복구 흐름은 다음과 같다.

1. 복구 가능한 거래인지 검증한다.
2. Bank의 거래 상태 조회 API를 호출한다.
3. Bank가 SUCCESS를 반환하면 BE 거래를 SUCCESS로 확정한다.
4. Bank가 FAILED를 반환하면 BE 거래를 FAILED로 확정한다.
5. Bank가 아직 PROCESSING이면 복구 시도 횟수만 증가시키고 다음 주기에 재시도한다.
6. Bank가 404를 반환하면 Bank에 기록이 없다고 보고 FAILED로 보정한다.

복구는 `transactionUuid` 기준으로 수행한다. timeout 발생 시 txHash를 받지 못했을 수 있으므로 txHash보다 UUID가 더 안정적인 조회 기준이다.

### 2.11 결제 취소 로직

취소는 원 결제 transactionId를 기준으로 수행한다.

주요 구성은 다음과 같다.

1. `executeCancel()`
2. `CancelLockManager`
3. `CancelIdempotencyStore`
4. `CancelExecutionStateWriter`
5. `CancelRequestHashGenerator`

취소 흐름은 다음과 같다.

1. 원 결제 거래를 조회한다.
2. 원 결제 UUID 기준 Redis 취소 락을 획득한다.
3. 원 결제 UUID와 가맹점 partyId로 requestHash를 만든다.
4. Redis cancel idempotency store에서 중복/충돌/처리중 여부를 판단한다.
5. 취소 가능 권한과 상태를 검증한다.
6. CANCEL 타입 거래를 새로 생성하고 PROCESSING으로 저장한다.
7. Bank 취소 API를 호출한다.
8. Bank 응답을 SUCCESS/UNKNOWN/FAILED로 분류한다.
9. 성공 응답 snapshot을 저장한다.

원 결제 row 자체를 CANCELED로 바꾸는 방식이 아니라, 취소 거래를 별도 `TransactionType.CANCEL`로 남기는 구조다. 이 방식은 감사 추적과 원장 일관성에 유리하다.

### 2.12 충전 로직

충전은 `domain/transaction/service/charge`에 구현되어 있다.

1. `ChargeCommandService`: 충전 의도 생성/실행
2. `ChargeExecutionWriter`: 충전 상태 변경
3. `ChargeQueryService`: 충전 내역 조회
4. `ChargeIdempotencyStore`: 충전 실행 멱등성
5. `ChargeRequestHashGenerator`: 요청 hash 생성
6. `RedisChargeIdempotencyStore`: Redis 기반 멱등성 저장소

충전은 계좌에서 지역화폐 지갑으로 자산을 이동시키는 성격이므로, 결제와 마찬가지로 중복 실행을 막아야 한다. Redis에 PROCESSING/SUCCESS/FAILED 상태와 응답 snapshot을 저장한다.

### 2.13 환전 로직

환전은 `domain/transaction/service/exchange`에 구현되어 있다.

1. `ExchangeCommandService`: 환전 요청 실행
2. `ExchangeStateWriter`: 상태 저장
3. `ExchangeQueryService`: 환전 내역 조회
4. `ExchangeReconcileService`: 불명확 상태 재확인
5. `RedisExchangeIdempotencyStore`: Redis 멱등성 저장소
6. `ExchangeRequestHashGenerator`: 요청 hash 생성

환전은 지역화폐를 은행 계좌로 되돌리는 흐름이다. Bank 호출 결과가 불명확할 수 있으므로 `BankActResult`를 SUCCESS/FAILURE/UNKNOWN으로 분류하고, UNKNOWN은 reconcile 대상이 된다.

### 2.14 Redis 멱등성 처리

BE는 Redis를 여러 방식으로 사용한다.

1. Spring Session 저장소
2. 결제 실행 멱등성 저장소
3. 결제 의도 dedup 저장소
4. 결제/취소 분산 락
5. 충전/환전 멱등성 저장소
6. Rate limit 저장소
7. ShedLock 스케줄러 락 provider

멱등성 저장소는 단순히 `"1"`만 저장하지 않고 다음 정보를 저장한다.

1. `transactionUuid`
2. `requestHash`
3. `transactionId`
4. 현재 상태
5. 응답 snapshot

판정 방식은 다음과 같다.

```text
기록 없음
  -> 신규 요청으로 처리

같은 key + 같은 requestHash + PROCESSING
  -> 처리 중 응답 또는 409

같은 key + 같은 requestHash + responseSnapshot 존재
  -> 기존 성공 응답 재사용

같은 key + 같은 requestHash + FAILED
  -> 이미 실패한 요청으로 재시도 거절

같은 key + 다른 requestHash
  -> IDEMPOTENCY_CONFLICT
```

`requestHash`를 함께 저장하는 이유는 같은 UUID로 금액이나 가맹점이 다른 요청을 보내는 충돌을 막기 위해서다.

### 2.15 Redis 분산 락

결제 실행과 취소 실행은 Redis 분산 락으로 감싼다.

1. 결제: `RedisPaymentLockManager`
2. 취소: `RedisCancelLockManager`

알고리즘은 `SET NX PX` 방식이다.

```text
SET lockKey randomToken NX PX ttl
```

락 해제는 compare-and-delete Lua 스크립트를 사용한다.

```text
현재 Redis value가 내가 발급한 token과 같을 때만 DEL
```

이 방식은 TTL 만료 후 다른 요청이 새 락을 잡았는데, 이전 요청이 늦게 종료되며 남의 락을 지우는 문제를 막는다.

### 2.16 Rate Limit

`RedisPaymentRateLimiter`는 Redis Lua script를 사용한다.

사용 알고리즘은 두 가지다.

1. Token Bucket
2. Sliding Window

Token Bucket은 결제 의도 생성이나 Bank outbound처럼 burst를 어느 정도 허용하면서 평균 처리량을 제한할 때 사용한다.

Sliding Window는 결제 실행/복구처럼 특정 시간 창 안의 정확한 요청 횟수 제한이 필요할 때 사용한다.

Redis Lua를 사용하는 이유는 카운트 조회, 증가, TTL 갱신이 한 번의 원자적 연산으로 실행되어 race condition을 줄일 수 있기 때문이다.

### 2.17 Scheduler와 ShedLock

BE에는 만료/복구/reconcile 스케줄러가 있다.

1. `PaymentIntentExpiryScheduler`: 오래된 PENDING 결제 의도 만료 처리
2. `ChargeIntentExpiryScheduler`: 충전 의도 만료 처리
3. `ReconcileScheduler`: 환전 등 불명확 상태 확인
4. `UnknownPaymentRecoveryScheduler`: UNKNOWN 결제 복구

ShedLock Redis provider를 사용해 여러 WAS 인스턴스가 떠 있어도 같은 스케줄 작업이 동시에 여러 번 실행되지 않도록 한다.

### 2.18 QR 코드 생성

BE는 ZXing 라이브러리를 사용한다.

가맹점 QR은 `MerchantQrService`에서 생성한다. QR payload는 가맹점 식별자와 결제에 필요한 정보를 담고, FE의 QR 스캔 화면에서 이를 읽어 결제 확인 화면으로 이동한다.

### 2.19 조회와 커서 페이지네이션

거래 내역, 결제 내역, 환전 내역, 충전 내역 조회에는 cursor pagination 구조가 있다.

관련 클래스는 다음과 같다.

1. `CursorPageRequest`
2. `CursorPageResponse`
3. `CursorItem`
4. `PaginationService`
5. `PaginationServiceImpl`

커서 페이지네이션은 offset 방식보다 대량 데이터에서 안정적이다. 최신 거래부터 조회하고, 마지막 item의 cursor를 다음 요청 기준으로 사용한다.

### 2.20 관측성

BE도 Bank와 동일하게 Actuator, Prometheus, Sentry, MDC logging을 사용한다.

`RequestIdPropagationInterceptor`는 BE가 Bank를 호출할 때 requestId를 전파해 두 서버의 로그를 연결할 수 있게 한다.

## 3. `hangang-pay-fe` 폴더

### 3.1 역할과 책임

`hangang-pay-fe`는 React 19 기반 SPA다. 모바일 앱처럼 사용할 수 있는 사용자/가맹점 화면을 제공한다.

주요 기능은 다음과 같다.

1. 로그인/회원가입
2. 사용자 홈, 잔액, 거래 내역
3. QR 스캔 기반 결제
4. 결제 PIN 입력, 처리중, 완료 화면
5. 충전
6. 환전/환불 성격의 플로우
7. 계좌 관리
8. 가맹점 홈
9. 가맹점 QR 표시
10. 가맹점 결제 내역과 상세
11. 가맹점 정산/환전

### 3.2 주요 폴더 구조

```text
hangang-pay-fe/src/
├─ api/             # BE API client와 도메인별 API 함수
├─ app/             # router, providers, root error element
├─ auth/            # 현재 사용자 hook, auth type
├─ components/      # 공통 UI 컴포넌트
├─ lib/             # format, uuid, navigation, utility
├─ mocks/           # MSW handler와 fixture
├─ pages/           # 라우트 단위 화면
├─ routes/          # layout, route guard
├─ main.tsx
├─ App.tsx
└─ index.css
```

### 3.3 API 계층

`src/api/client.ts`는 공통 fetch wrapper다.

특징은 다음과 같다.

1. `VITE_API_BASE_URL + /api/v1`을 base URL로 사용한다.
2. `credentials: 'include'`로 세션 쿠키를 포함한다.
3. 서버 공통 응답 형태인 `{ isSuccess, code, message, result }`를 해석한다.
4. 401이 발생하면 localStorage의 role을 제거하고 `/login`으로 이동한다.
5. 서버 응답의 `isSuccess === false`는 `ApiError`로 변환한다.

도메인별 API 파일은 다음과 같다.

1. `auth.ts`: 로그인/로그아웃/회원가입 관련
2. `accounts.ts`: 계좌 관리
3. `wallet.ts`: 잔액/지갑 조회
4. `payment.ts`: 결제 의도/실행/취소
5. `charge.ts`: 충전

## 4. `nginx` 폴더

### 4.1 역할

`nginx` 폴더는 배포 환경에서 FE 정적 파일을 서빙하고 BE API로 프록시하기 위한 설정을 담고 있다.

파일은 다음 하나다.

```text
nginx/hangang-pay.conf
```

### 4.2 서버 설정

설정 내용은 다음과 같다.

```nginx
server {
    listen 80;
    server_name 172.21.33.235;

    root /var/www/hangang-pay;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://10.10.1.76:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

### 4.3 SPA fallback

`location /`의 `try_files $uri $uri/ /index.html;`은 React Router를 위한 설정이다.

브라우저가 `/merchant/home` 같은 경로로 직접 접근하면 서버 파일 시스템에는 해당 파일이 없다. 이때 nginx가 404를 반환하지 않고 `index.html`을 내려주면, React Router가 클라이언트에서 경로를 해석한다.

### 4.4 API reverse proxy

`location /api/`는 BE 서버로 프록시한다.

1. 클라이언트는 같은 origin의 `/api/...`로 요청한다.
2. nginx는 `http://10.10.1.76:8080`으로 전달한다.
3. `Host`, `X-Real-IP`, `X-Forwarded-For` 헤더를 함께 전달한다.

이 구조는 FE와 BE를 같은 도메인처럼 보이게 해 CORS와 쿠키 세션 문제를 줄인다.

## 5. 고급 기술과 핵심 설계 정리

### 5.1 Redis

이 프로젝트에서 Redis는 단순 캐시가 아니라 결제 안정성을 위한 핵심 인프라다.

사용처는 다음과 같다.

1. Spring Session 저장소
2. 결제 실행 멱등성 저장소
3. 취소/충전/환전 멱등성 저장소
4. 결제 의도 dedup 저장소
5. Redis 분산 락
6. Rate limit counter 저장소
7. ShedLock provider

Redis를 사용하는 이유는 빠른 원자 연산과 TTL 때문이다. 특히 `SET NX`, Lua script, TTL을 조합해 중복 요청과 동시 요청을 처리한다.

### 5.2 멱등성

멱등성은 같은 요청이 여러 번 들어와도 실제 결과가 한 번만 반영되도록 하는 성질이다.

프로젝트는 다층 방어를 사용한다.

1. FE: 버튼 중복 클릭과 처리 중 화면으로 UX 차단
2. BE: Redis idempotency store와 requestHash
3. BE: Redis distributed lock
4. BE DB: `transactionUuid` 기반 거래 상태 관리
5. Bank DB: 원장 unique constraint
6. Blockchain: 컨트랙트 `processedTx` 또는 bytes32 UUID 기반 중복 방지

하나의 계층만 믿지 않고 여러 계층에서 중복을 막는 것이 핵심이다.

### 5.3 동시성 제어

동시성 제어는 다음 조합으로 구현되어 있다.

1. Redis 분산 락: 여러 WAS 인스턴스의 같은 거래 동시 실행 차단
2. DB 비관적 락: 실제 잔액 row의 동시 수정 차단
3. DB unique constraint: 최종 중복 저장 방지
4. 상태 머신: PENDING/PROCESSING/SUCCESS/FAILED/UNKNOWN/EXPIRED 전이 제한
5. Outbox: DB 변경과 MQ 발행 사이의 유실 방지

Redis 락은 빠른 1차 방어선이고, DB 제약은 마지막 방어선이다.

### 5.4 Rate Limit 알고리즘

프로젝트는 Token Bucket과 Sliding Window를 구분해 사용한다.

Token Bucket은 burst를 허용하면서 평균 처리량을 제한한다.

```text
토큰이 일정 속도로 채워짐
요청마다 토큰 1개 소비
토큰이 있으면 허용
토큰이 없으면 차단
```

Sliding Window는 최근 N초/N분의 정확한 요청 횟수를 제한한다.

```text
현재 시각 기준 window 밖의 기록 제거
남은 요청 수 계산
limit보다 작으면 현재 요청 기록 후 허용
limit 이상이면 차단
```

Redis Lua script로 구현해 조회/삭제/추가/TTL 갱신을 원자적으로 처리한다.

### 5.5 Outbox + RabbitMQ

블록체인 제출은 시간이 오래 걸리고 실패 가능성이 높다. 그래서 API 요청 스레드에서 직접 확정까지 기다리지 않고 Outbox와 RabbitMQ를 사용한다.

장점은 다음과 같다.

1. 사용자 응답 속도 개선
2. DB 반영과 메시지 발행 사이의 유실 방지
3. retry/DLQ를 통한 장애 격리
4. txHash checkpoint로 중복 제출 방지
5. 블록체인 노드 장애가 플랫폼 API 전체 장애로 번지는 것을 완화

### 5.6 상태 머신

결제 시스템에서는 단순 성공/실패만으로는 부족하다. 외부 시스템 호출이 포함되기 때문에 결과 불명확 상태가 필요하다.

BE는 `UNKNOWN` 상태를 두고, Bank는 `SUBMITTED` 상태를 둔다.

1. BE `UNKNOWN`: Bank 호출 결과를 모름
2. Bank `SUBMITTED`: 블록체인 txHash는 받았지만 receipt 최종 결과는 아직 모름

이 중간 상태 덕분에 timeout을 실패로 오판하지 않고, 후속 조회/reconcile로 최종 상태를 확정할 수 있다.

### 5.7 블록체인 구조

`hangang-pay-bc`에는 Besu 네트워크와 Hardhat/Solidity 컨트랙트가 있다.

주요 컨트랙트는 다음과 같다.

1. `BaseToken.sol`: 토큰 공통 기반
2. `CBDCToken.sol`: CBDC 성격 토큰
3. `DepositToken.sol`: 예치/지역화폐 토큰
4. `LocalCurrencyPolicy.sol`: 결제, 가맹점 검증, 중복 transaction 처리
5. `Settlement.sol`: 정산 관련 컨트랙트

Bank 서버는 Web3j로 이 컨트랙트 함수를 호출한다. UUID는 bytes32로 변환되어 컨트랙트에 전달되고, 컨트랙트는 이미 처리한 UUID를 다시 처리하지 않도록 한다.

### 5.8 관측성

BE와 Bank는 모두 관측성을 고려해 구성되어 있다.

1. Actuator: health, metrics endpoint
2. Micrometer Prometheus registry: Prometheus scrape용 metric 노출
3. Alloy: 로그/metric 수집 설정
4. Grafana Cloud/Loki: 로그와 metric 관찰
5. Sentry: 예외 추적과 성능 tracing
6. MDC: requestId, partyId, role 등 로그 상관관계

분산 시스템에서는 한 요청이 FE, BE, Bank, MQ, Blockchain으로 이어지므로 requestId 전파와 MDC 로깅이 중요하다.

### 5.9 배포 관련 구성

BE와 Bank에는 Dockerfile, deploy docker-compose, appspec, start/stop/validate script가 포함되어 있다. 이는 EC2/CodeDeploy 계열 배포와 컨테이너 실행을 고려한 구성이다.

프론트엔드는 Vercel 설정(`vercel.json`)과 Vite build 구성이 있다. nginx는 별도 정적 배포 환경에서 SPA fallback과 API proxy 역할을 한다.

## 6. 전체 거래 흐름 요약

### 6.1 사용자 결제

```text
FE QR 스캔
-> BE 결제 의도 생성(PENDING, transactionUuid 발급)
-> FE PIN 입력
-> BE Redis 락/멱등성 확인
-> BE 거래 PROCESSING 전환
-> BE가 Bank 결제 API 호출
-> Bank DB 지갑 원장 반영
-> Bank BlockchainLedger/Outbox 저장
-> BE SUCCESS 또는 UNKNOWN 반영
-> Outbox scheduler가 RabbitMQ 발행
-> Consumer가 Web3j로 컨트랙트 pay 호출
-> txHash SUBMITTED 저장
-> receipt 확인
-> Bank BlockchainLedger SUCCESS/FAILED 확정
```

### 6.2 사용자 충전

```text
FE 충전 금액 입력
-> FE PIN 입력
-> BE 충전 API 호출
-> BE 멱등성 확인
-> BE가 Bank charge API 호출
-> Bank 계좌/지갑 검증
-> Bank 계좌 원장/지갑 원장 기록
-> Bank 블록체인 mint 요청
-> 최종 상태 저장
-> FE 완료 화면
```

### 6.3 가맹점 정산/환전

```text
FE 가맹점 정산 요청
-> BE 환전 API 호출
-> BE 멱등성 확인
-> BE가 Bank exchange API 호출
-> Bank 지갑 차감 및 계좌 입금 계열 처리
-> 블록체인 burn/refund 요청 outbox 저장
-> RabbitMQ consumer가 컨트랙트 호출
-> receipt 기준 최종 상태 확정
-> BE reconcile로 UNKNOWN 상태 보정
```

### 6.4 결제 취소

```text
가맹점 결제 상세에서 취소 요청
-> BE 원 결제 조회
-> BE 원 결제 UUID 기준 취소 락 획득
-> BE 취소 멱등성 확인
-> BE CANCEL 거래 생성
-> BE가 Bank cancel API 호출
-> Bank 가맹점 지갑 -> 사용자 지갑 반대 이체
-> Bank 취소 원장/outbox 저장
-> 블록체인 cancel submit
-> receipt 기준 SUCCESS/FAILED 확정
```

## 7. 코드 구성상의 핵심 의도

이 프로젝트의 핵심 설계 의도는 다음과 같다.

1. 플랫폼 API와 은행/BaaS 책임을 분리한다.
2. 실제 자산 변경은 Bank 서버에서 최종 검증한다.
3. BE는 사용자 경험과 거래 상태 머신을 관리한다.
4. 블록체인 확정은 비동기로 분리해 API 지연을 줄인다.
5. Redis, DB unique, 컨트랙트 processedTx로 중복 결제를 다층 방어한다.
6. UNKNOWN/SUBMITTED 상태를 둬 외부 호출 불확실성을 복구 가능하게 만든다.
7. requestHash와 responseSnapshot으로 멱등성 응답을 재사용한다.
8. Rate Limit은 중복 방지 수단이 아니라 과도한 요청 완화 수단으로 사용한다.
9. Outbox와 RabbitMQ로 메시지 유실과 블록체인 장애 전파를 줄인다.
10. Actuator/Sentry/Prometheus/MDC로 장애 분석 가능성을 확보한다.
